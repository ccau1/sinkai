# Cloudflare Deployment

This folder contains Terraform configuration and deployment helpers for running the Sin Kai stack on Cloudflare:

- **Public website** (`packages/web`) → Cloudflare Pages
- **Payload CMS** (`packages/cms`) → Cloudflare Worker
- **Database** → Cloudflare D1
- **Media uploads** → Cloudflare R2

The pipeline follows the same promote-to-prod pattern as the Hetzner workflows:

1. Every push to `main` deploys to **staging** automatically.
2. The **production** job requires manual approval via the GitHub `production` environment.

## Infrastructure

Terraform provisions:

- D1 databases: `sinkai-cms-prod`, `sinkai-cms-staging`
- R2 buckets: `sinkai-cms-media-prod`, `sinkai-cms-media-staging`, each attached to a public custom domain (`sinkai-cms-media[.staging].tribalorigin.com`)
- A WAF custom rule (`waf.tf`) blocking public access to the `/private/` prefix on the media domains
- Pages projects:
  - `sinkai-web` (production) → `sinkai.tribalorigin.com`
  - `sinkai-web-staging` (staging) → `sinkai.staging.tribalorigin.com`
- CMS subdomains (`sinkai-cms.tribalorigin.com`, `sinkai-cms.staging.tribalorigin.com`) are managed by Wrangler via `packages/cms/wrangler.jsonc`

Planned URLs:

| Environment | Web | CMS |
|-------------|-----|-----|
| Production | `https://sinkai.tribalorigin.com` | `https://sinkai-cms.tribalorigin.com` |
| Staging | `https://sinkai.staging.tribalorigin.com` | `https://sinkai-cms.staging.tribalorigin.com` |

## Prerequisites

- Cloudflare account with R2 enabled
- Cloudflare API token with permissions for:
  - Cloudflare Pages (Edit)
  - Cloudflare Workers Scripts (Edit)
  - D1 (Edit)
  - R2 (Edit)
  - Zone:Read and DNS:Edit for `tribalorigin.com`
  - Zone WAF:Edit for `tribalorigin.com` (required by the `cloudflare_ruleset` in `waf.tf`)
- Terraform >= 1.5
- Wrangler CLI authenticated (`npx wrangler login`)

## Initial Setup

1. Copy the Terraform variables example and fill in your values:

   ```bash
   cd cloudflare_deploy/terraform
   cp terraform.tfvars.example terraform.tfvars
   # Edit terraform.tfvars
   ```

2. Apply the Terraform configuration:

   ```bash
   terraform init
   # The R2 custom-domain provisioners (r2.tf) call the Cloudflare API via
   # curl and read the token from the shell environment (never from state):
   export CLOUDFLARE_API_TOKEN=<same token as in terraform.tfvars>
   terraform apply
   ```

3. Note the outputs (`d1_database_id_prod`, `d1_database_id_staging`, `r2_bucket_name_prod`, `r2_bucket_name_staging`).

4. Update `packages/cms/wrangler.jsonc` with the Terraform outputs (only the D1 IDs need to change; R2 bucket names are already hard-coded).

5. Ensure Terraform manages the DNS records for the web domains:

   `cloudflare_deploy/terraform/dns.tf` creates CNAME records that point
   `sinkai.tribalorigin.com` and `sinkai.staging.tribalorigin.com` to the
   Cloudflare Pages projects. If a stale A record exists (for example pointing
   to a previous Hetzner server), it will be overwritten.

6. Set GitHub secrets:

   - `CLOUDFLARE_API_TOKEN`
   - `CLOUDFLARE_ACCOUNT_ID`
   - `CLOUDFLARE_ZONE_ID` (zone ID for `tribalorigin.com`)
   - `PAYLOAD_SECRET` (used for both staging and prod Workers)
   - `CMS_API_URL_PROD` → `https://sinkai-cms.tribalorigin.com`
   - `CMS_API_URL_STAGING` → `https://sinkai-cms.staging.tribalorigin.com`

7. Enable **Image Transformations** for `tribalorigin.com` in the Cloudflare dashboard:

   - Go to **Speed → Images → Transformations** and toggle it on.
   - Under **Sources**, allow the CMS origins:
     - `https://sinkai-cms.tribalorigin.com`
     - `https://sinkai-cms.staging.tribalorigin.com`

8. Push to `main`. The CMS workflow deploys and seeds first; the web workflow then rebuilds against the updated CMS. Approve the `production` environment to promote to prod.

## Notes

- The CMS Next.js app is built with webpack rather than Turbopack, because the
  OpenNext Cloudflare bundler currently panics on the dynamic `import()` pattern
  generated by Turbopack for local Wrangler platform-proxy code.
- `PAYLOAD_REMOTE=true` is required when running Payload CLI commands (migrate,
  seed) against the remote D1/R2 bindings.
- The web workflow is triggered both by web-code changes and by successful
  completions of the CMS workflow. This prevents the static site from being
  built before the CMS has finished migrating/seeding.
- CMS media is served from a public R2 custom domain
  (`sinkai-cms-media[.staging].tribalorigin.com`). Originals under `public/`
  and generated thumbnails under `public/thumbnails/` are publicly accessible.
  Objects under the `private/` prefix are blocked by a WAF custom rule
  (`waf.tf`) and are only served through the CMS Worker
  (`/api/media/file/...?prefix=private`) for logged-in users.
  - Note: the zone-scoped ruleset in `waf.tf` manages the entire
    `http_request_firewall_custom` phase for the zone, so any other custom
    firewall rules must be added there as well.
- Thumbnails are generated by the thumbnail workflow worker
  (`sinkai-cms-thumbnails-[staging|prod]`), which writes `public/thumbnails/*.webp`
  into the media bucket.
- The frontend uses Cloudflare Images transformations (`/cdn-cgi/image/...`) to
  resize and optimise images on demand. The first 5,000 unique transformations
  per month are free.

## Local Development

```bash
# Terminal 1 — CMS
PAYLOAD_SECRET=local-dev-secret npm run dev -w packages/cms

# Terminal 2 — web (calls CMS at http://localhost:3001)
CMS_API_URL=http://localhost:3001 npm run dev -w packages/web
```

Or run both via Docker:

```bash
make up
```

- Web: http://localhost:3200
- CMS: http://localhost:3001
